System Architecture · v2 · Phase 6 frozen

Two parallel agents, one chat pipeline.

每条用户消息走同一条 Check → Route → Generate → Validate → Publish 主线。 区别只在 Route 这一步：round.facilitation 是 static 就走 STATIC 通道，adaptive 就跑 Assessor 决定 4 选 1。 Static 和 Adaptive 不互通，连 prompt 都是独立的。

1. Top level — two agents, no overlap

round.facilitation 决定走哪条主线。两条线在 Generator 之前互不相干，prompt 模板、role 枚举、abstain 策略都是各自独立。

A. Static
Fixed prompt · 每条必发

无 Assessor，无 abstain。每条消息满足频控就强制生成并 publish。

prompt: static.md同 Generator 同一份 base + role 段

decision enum 不参与 · 没有 generalist/specialist 概念

2. 每条消息的生命周期

从用户在 chat 里发消息，到 llmLog 多一条 entry，完整流程。一次发送可能触发 1 次或 2 次 Generator 调用（带 repair）。

实线 = 正常路径 · 橙色虚线 = repair 循环（最多 1 次）· 红色虚线 = silent 失败路径

3. Validator — 7 frozen criteria

每条 Generator 输出都会被独立 LLM 调用打分。任何一个 true = fail，触发 repair。 frozen 不可改，evidenceChecker 那边复用同一份。

notGrounded不基于已说过的内容，引入外部事实
nonNeutral带价值判断 / 立场偏向
roleMisaligned做的事跟当前角色定义不符
inventedInformation捏造 chat 里没出现过的细节
recommendationDetected替用户做决策 / 给最终答案
unsupportedInformationDetected提到的事找不到 source
unsupportedConsensusClaim宣称"大家都同意 X"但没人说过

4. CheckpointManager — 频控规则

每条消息进 pipeline 之前先过这 6 条 gate。任何一条失败就 silent 跳过（不消耗 opportunity）。 @[Facilitator] 是唯一绕过频控的通道。

1. chat readyrequired
stage 处于 chat 阶段，不在 intro / final decision / survey
2. stage == Taskrequired
只在 Task 阶段评估，Result / Debrief 阶段全部跳过
3. time floor10s
距离 round 开始 ≥ 10 秒，否则太早
4. intervention cap3 / round
硬上限，不可绕过（包括 @-mention）
5. cooldown30s
距离上次成功 publish ≥ 30s
6. opportunity gate≥ 6 msgs
距上次 evaluate ≥ 6 条新消息
⚡ @[Facilitator] mention bypassmention_bypass
新消息里出现 @[Facilitator] 时无条件放行：跳过 cooldown / opportunity gate / dedup，但仍尊重 cap / stage / time floor / chat ready。reason 记为 mention_bypass，llmLog 里能区分。
